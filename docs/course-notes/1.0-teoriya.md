# Теория (1.1–1.4): почему проект выглядит именно так

> Это не пересказ видео, а разбор тем: что стоит за каждым решением и как оно проросло
> в код `DevQuestions`. Читать полезно **после** практики 2.1–2.4 — тогда абстракции
> ложатся на уже знакомые файлы.

---

## 1.1 Придумывание идеи для проекта

Для учебного проекта по архитектуре важно не «что красиво выглядит», а **есть ли в домене
нетривиальные правила**. CRUD-приложение (создать/прочитать/обновить/удалить) не требует
ни слоёв, ни портов — для него Minimal API плюс `DbContext` в одном файле честнее любой
многослойности.

DevQuestions выбран потому, что в нём есть правила, которые некуда деть кроме доменного слоя:

- у пользователя не может быть больше 3 открытых вопросов одновременно
- вопрос закрывается выбором решения — и только автор может его выбрать
- ответ нельзя добавить в закрытый вопрос
- репорт на вопрос меняет его статус

Это **инварианты** — утверждения, которые должны быть истинны всегда. Как только в домене
появляются инварианты, появляется и вопрос «где их проверять», а вместе с ним — вся архитектура.

**Практический вывод для своих проектов:** прежде чем городить слои, спроси, есть ли
хоть одно правило, которое нельзя выразить CHECK-констрейнтом базы. Нет — не нужны слои.

## 1.2 Проектирование REST API

REST — это не «HTTP плюс JSON», а набор ограничений. На практике из них выживают четыре идеи.

### Ресурс — существительное, действие — HTTP-метод

```
GET    /api/questions            — коллекция
POST   /api/questions            — создать
GET    /api/questions/{id}       — элемент
PUT    /api/questions/{id}       — заменить целиком
PATCH  /api/questions/{id}       — изменить частично
DELETE /api/questions/{id}       — удалить
```

Плохо: `POST /api/createQuestion`, `GET /api/getQuestionById?id=1`. Глагол уже есть в методе.

### Вложенность отражает принадлежность

```
POST /api/questions/{questionId}/answers      — ответ живёт внутри вопроса
POST /api/questions/{questionId}/solution     — пограничный случай
```

Правило: вкладывать имеет смысл, если дочерний ресурс **не существует** без родителя.
Глубже двух уровней не лезут — читаемость падает быстрее, чем растёт польза.

### Коды ответов несут смысл

| Код | Когда |
|---|---|
| 200 OK | успех с телом |
| 201 Created | создано, в заголовке `Location` — ссылка на новый ресурс |
| 204 No Content | успех без тела (типично для DELETE) |
| 400 Bad Request | синтаксис или валидация не прошли |
| 404 Not Found | ресурса нет |
| 409 Conflict | конфликт состояния (например, лимит открытых вопросов) |
| 422 Unprocessable Entity | синтаксис верный, но бизнес-смысл — нет |

Про 400 против 409 против 422 спорят до сих пор. Договорённость важнее правоты: выбери схему
и держись её по всему API. Курс к этому вернётся в 2.5 «Обработка ошибок» — там как раз
появляется место, где это решение централизуется.

### Контракты отдельно от домена

В репозитории это проект `DevQuestions.Contracts` — DTO, которые уходят наружу:

```csharp
public record CreateQuestionDto(string Title, string Text, Guid UserId, IEnumerable<Guid> TagIds);
```

Почему не отдавать доменные сущности напрямую:

1. **Домен меняется чаще, чем контракт.** Переименовал поле в сущности — сломал всех клиентов.
2. **Домен знает лишнее.** Внутренние флаги, аудит, чужие идентификаторы утекут наружу
   без единой строчки кода.
3. **Формы разные.** На вход при создании нужен заголовок, но не идентификатор; на выход — наоборот.

Цена — ручное или автоматическое (Mapster, AutoMapper) отображение. Это осознанная плата,
а не бюрократия.

## 1.3 Монолит, модульный монолит, микросервисы

Главная мысль: **это не лестница «от плохого к хорошему»**, а выбор компромисса.

| | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Развёртывание | одно | одно | много независимых |
| Транзакции | обычные, ACID | обычные, ACID | распределённые, saga |
| Отладка | стек-трейс | стек-трейс | трассировка через сеть |
| Цена ошибки в границах | правка кода | правка кода | правка контракта плюс миграция данных |
| Масштабирование | целиком | целиком | по частям |
| Команды | одна | одна-две | много независимых |

Микросервисы решают **организационную** проблему (много команд не могут делить один
релизный цикл), а не техническую. Если команда одна, микросервисы дают всю цену
распределённой системы и ничего из пользы.

Модульный монолит — середина, к которой курс придёт в 2.10: границы модулей проведены
по-настоящему (отдельные сборки, свои схемы в БД, общение через контракты), но деплой один
и транзакции обычные. Если модуль позже придётся выделить — границы уже проведены, останется
заменить вызов метода на вызов по сети.

**Чек-лист, что пора дробить:** разные части требуют разного железа; релизы блокируют друг друга;
команды наступают друг другу на ноги в одних и тех же файлах; SLA разный. Ни один пункт
не звучит как «модно».

## 1.4 Чистая архитектура

Самое частое заблуждение — что Clean Architecture это «четыре папки». Она про **одно правило**:

> Зависимости направлены только внутрь. Внешний слой знает о внутреннем, внутренний о внешнем — никогда.

### Слои в этом репозитории

```
Domain          ← ничего не знает. Сущности, инварианты, перечисления.
   ↑
Application     ← знает Domain. Сценарии, интерфейсы (порты), валидация.
   ↑
Infrastructure  ← знает Application и Domain. EF Core, Dapper, S3, Elasticsearch.
   ↑
Web/Presenters  ← знает всех. Контроллеры, DI, middleware.
```

Проверяется это тривиально — по `ProjectReference` в `.csproj`. Если в
`DevQuestions.Domain.csproj` появится ссылка хоть на что-то — правило нарушено, и компилятор
об этом не скажет ни слова. Это единственный слой, который должен остаться пустым по ссылкам.

### Почему интерфейс репозитория лежит в Application, а не в Infrastructure

Ключевой приём всей архитектуры — **инверсия зависимостей**. Application нужен доступ к данным,
но зависеть от EF Core он не должен. Поэтому Application сам объявляет, что ему нужно:

```csharp
// src/DevQuestions.Application/Questions/IQuestionsRepository.cs — ПОРТ
public interface IQuestionsRepository
{
    Task<Guid> AddAsync(Question question, CancellationToken cancellationToken);
}
```

а Infrastructure приносит реализацию:

```csharp
// src/DevQuestions.Infrastructure.PostgreSql/Repositories/QuestionsEfCoreRepository.cs — АДАПТЕР
public class QuestionsEfCoreRepository : IQuestionsRepository { ... }
```

Стрелка зависимости при этом смотрит вверх: Infrastructure ссылается на Application, не наоборот.
Отсюда и название «инверсия» — естественное направление («тот, кто пользуется, зависит от того,
кем пользуется») перевёрнуто.

Что это даёт на самом деле, без лозунгов:

1. **Тесты Application не требуют базы.** Подставил заглушку `IQuestionsRepository` — и сценарий
   проверяется в памяти за миллисекунды.
2. **Замена технологии не трогает бизнес-логику.** Postgres на MongoDB меняет один проект.
3. **Границу видно.** Список портов в Application — это ровно список всего, что проект требует
   от внешнего мира. Он помещается на один экран и читается как техническое задание.

Пункт 2 на практике срабатывает реже, чем обещают в книгах — базы меняют раз в пятилетку.
Пункты 1 и 3 окупают приём почти всегда.

### Порты и адаптеры — то же самое другими словами

Гексагональная архитектура (Алистер Кокбёрн) и Clean Architecture (Роберт Мартин) описывают
один механизм. «Порт» — интерфейс, который объявляет потребитель; «адаптер» — реализация
под конкретную технологию. В 2.4 этот приём применяется уже к трём вещам сразу:
`IQuestionsRepository` к Postgres, `ISearchProvider` к Elasticsearch, `IFileProvider` к S3.

### Где Clean Architecture вредит

Честный список, потому что в видео его обычно нет:

- **CRUD без правил.** Пять слоёв ради выборки списка тегов — чистый оверхед.
- **Анемичный домен.** Если сущности — мешки свойств, а вся логика в сервисах, то это
  не Clean Architecture, а транзакционный скрипт с лишними папками. Посмотри на `Question`:
  есть ли у него методы, меняющие состояние, или только свойства с публичными сеттерами?
- **Абстракция ради абстракции.** Интерфейс с одной реализацией, которую никогда не заменят
  и которую невозможно осмысленно подменить в тесте, — это просто лишний файл.

Критерий полезности порта простой: **можно назвать вторую реализацию, и она осмысленна**
(вторая БД, заглушка в тесте, другой вендор). Нельзя — интерфейс, скорее всего, лишний.
