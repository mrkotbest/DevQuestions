## Теория: что такое слой приложения

Самый частый вопрос на этом этапе — чем Application отличается от Domain, если бизнес-логика
вроде бы и там, и там.

Разграничение такое:

| | Domain | Application |
|---|---|---|
| Отвечает на вопрос | «что истинно всегда» | «что происходит, когда пользователь нажал кнопку» |
| Содержит | сущности, инварианты, правила внутри одного объекта | сценарии: последовательность шагов |
| Знает про | ничего | домен и порты во внешний мир |
| Пример | «вопрос не может иметь пустой заголовок» | «проверить ввод → посчитать открытые вопросы → создать → сохранить → проиндексировать → записать в лог» |

Application-слой — это **оркестровка**. Он не содержит собственных бизнес-правил, он расставляет
в правильном порядке чужие: правила домена, обращения к хранилищу, к поиску, к логу.

В литературе такой класс называют по-разному: application service, use case, interactor,
command handler. В курсе он начинается как `QuestionsService` с методами, а на видео 2.8
превратится в отдельные обработчики — по классу на сценарий. Это естественная эволюция:
пока сценариев три, сервис удобнее; когда их тридцать, класс на две тысячи строк никому
не нужен.

## Разбор по шагам

### Зависимости проекта

```xml
<ProjectReference Include="..\DevQuestions.Contracts\..." />
<ProjectReference Include="..\DevQuestions.Domain\..." />

<PackageReference Include="FluentValidation.DependencyInjectionExtensions" Version="12.1.1" />
<PackageReference Include="Microsoft.Extensions.Logging.Abstractions" Version="10.0.12" />
```

Обрати внимание на слово **Abstractions** во втором пакете. Это библиотека, в которой есть
только интерфейсы: `ILogger<T>`, `LogLevel`, и нет ни одной реализации — ни консольного
вывода, ни файлов, ни Serilog.

Это тот же приём инверсии зависимостей, только с готовой абстракцией от Microsoft: слой
сценариев объявляет «мне нужно куда-то писать», а **чем** писать решает хост. Поменять
логирование на Serilog можно, не тронув ни строчки в Application.

Такие пакеты с суффиксом `.Abstractions` есть у большинства библиотек Microsoft — это
общепринятый способ дать библиотеке зависимость на контракт, а не на реализацию.

### Сервис и его интерфейс

```csharp
public interface IQuestionsService
{
    Task<Guid> Create(CreateQuestionDto createQuestionDto, CancellationToken cancellationToken);
}
```

Интерфейс объявлен ровно под то, что нужно контроллеру. Остальные методы (`Update`, `Delete`,
`SelectSolution`, `AddAnswer`) существуют в классе как заготовки под следующие видео.

Зачем вообще интерфейс, если реализация одна? Две причины, и обе практические:

1. **Presenters не зависит от Application-реализации.** Контроллер видит контракт, а какой
   класс за ним стоит — дело корня композиции.
2. **Тест контроллера не требует настоящего сервиса.** Заглушка `IQuestionsService` —
   и та самая «вторая реализация», о которой говорят при обсуждении пользы интерфейсов.

### Валидация

```csharp
public class CreateQuestionValidator : AbstractValidator<CreateQuestionDto>
{
    public CreateQuestionValidator()
    {
        RuleFor(q => q.Title).NotEmpty().MaximumLength(500).WithMessage("...");
        RuleFor(q => q.Text).NotEmpty().MaximumLength(5000).WithMessage("...");
        RuleFor(q => q.UserId).NotEmpty();
    }
}
```

`NotEmpty()` на `Guid` отсекает `Guid.Empty` — для структуры это и есть «пустое значение»,
`null` там быть не может.

#### Теория: два разных вида проверок

Их регулярно смешивают, а разница принципиальная.

**Валидация входных данных** — проверка формы сообщения, без обращения к системе.
«Заголовок не пуст», «длина не больше 500», «email похож на email». Ответ на вопрос
«это вообще осмысленный запрос?». Проверяется мгновенно, не требует ни базы, ни контекста.

**Бизнес-правило** — проверка состояния системы. «У пользователя уже три открытых вопроса»,
«вопрос уже закрыт», «такой тег не существует». Требует обращения к данным и зависит от
момента времени: минуту назад ответ мог быть другим.

В коде это видно буквально:

```csharp
// валидация входа — FluentValidation, ничего не знает о системе
var validationResult = await _createQuestionValidator.ValidateAsync(questionDto, cancellationToken);

// бизнес-правило — нужен поход в хранилище
int openUserQuestionsCount = await _questionsRepository
    .GetOpenUserQuestionsCountAsync(questionDto.UserId, cancellationToken);
```

Почему их не стоит объединять: валидатор должен оставаться быстрым и чистым, иначе он
превращается в ещё один сервис со своими зависимостями и перестаёт быть проверяемым в отрыве
от базы.

#### Почему валидация вызывается вручную, а не фильтром MVC

У FluentValidation есть режим автоматической валидации — `AddFluentValidationAutoValidation()`,
когда проверка выполняется конвейером MVC до входа в контроллер. Автор им не пользуется,
и это осознанный выбор:

1. **Правила валидации — часть сценария, а не часть HTTP.** Если завтра `Create` вызовут
   из фонового задания, консольной утилиты или обработчика очереди, проверки поедут вместе
   с ним. При валидации в конвейере они остались бы в вебе.
2. **Видно в коде.** Открыв метод, ты видишь, что он валидирует вход. Автоматическая валидация
   через фильтр в теле метода невидима — про неё надо просто знать.
3. **Тест сценария покрывает и валидацию.**

Плата — три строки в начале каждого сценария. Когда сценариев станет много, это повторение
уберут в декоратор (видео 2.10) — то есть валидация останется частью Application, но перестанет
дублироваться.

#### Регистрация сканированием

```csharp
services.AddValidatorsFromAssembly(typeof(DependecyInjection).Assembly);
```

Один вызов находит в сборке все наследники `AbstractValidator<T>` и регистрирует их как
`IValidator<T>`. Именно поэтому в конструктор сервиса внедряется `IValidator<CreateQuestionDto>`,
а не конкретный `CreateQuestionValidator`.

Приём называется **assembly scanning**, и это компромисс: новый валидатор подключается сам,
без правки регистраций, но зато состав контейнера больше не виден в коде явно. На видео 2.8
тем же способом (через библиотеку Scrutor) будут регистрироваться обработчики команд.

### Внедрение зависимостей в сервис

```csharp
public QuestionsService(
    IQuestionsRepository questionsRepository,
    IValidator<CreateQuestionDto> createQuestionValidator,
    ILogger<QuestionsService> logger)
```

Три зависимости, все — интерфейсы, все `readonly`-поля. Сервис не создаёт ничего сам
и не знает, что стоит за контрактами.

Полный разбор механики — в [теории про DI](teoriya-dependency-injection.md). Здесь достаточно
одного наблюдения: длина списка параметров конструктора работает как бесплатный индикатор.
Три-четыре зависимости — норма; когда их станет восемь, это будет сигналом, что класс делает
слишком много.

### Композиция зависимостей в два уровня

```csharp
// Application знает, что регистрировать ему
public static IServiceCollection AddApplication(this IServiceCollection services)
{
    services.AddValidatorsFromAssembly(typeof(DependecyInjection).Assembly);
    services.AddScoped<IQuestionsService, QuestionsService>();

    return services;
}

// хост только собирает слои вместе
public static IServiceCollection AddProgramDependencies(this IServiceCollection services)
{
    services.AddWeb();
    services.AddApplication();

    return services;
}
```

Смысл приёма: добавляя сервис, правишь файл **того слоя**, которому он принадлежит. Хост
не знает состава слоёв — только их имена. На видео 2.10 эта же конструкция превратится
в `AddQuestionsModule()`, `AddTagsModule()`, то есть масштабируется без переписывания.

Почему `Scoped`, а не `Transient` или `Singleton`: сервис работает в связке с `DbContext`,
который живёт один HTTP-запрос. Один экземпляр на запрос означает общую единицу работы
и общую транзакцию для всех участников этого запроса.

Заодно `Program.cs` худеет — из него ушли `AddControllers()` и `AddOpenApi()`, спрятанные
в приватный `AddWeb()`. Точка входа должна оставаться местом, где видно устройство приложения
целиком, а не свалкой регистраций.

### Порт репозитория появляется раньше реализации

```csharp
public interface IQuestionsRepository
{
    Task<Guid> AddAsync(Question question, CancellationToken cancellationToken);
    Task<Guid> DeleteAsync(Guid questionId, CancellationToken cancellationToken);
    Task<Guid> SaveAsync(Question question, CancellationToken cancellationToken);
    Task<Question> GetByIdAsync(Guid questionId, CancellationToken cancellationToken);
    Task<int> GetOpenUserQuestionsCountAsync(Guid userId, CancellationToken cancellationToken);
}
```

Реализация появится только на следующем видео — и это правильный порядок, а не недоделка.

**Форму порта диктует сценарий, а не база данных.** Метод называется
`GetOpenUserQuestionsCountAsync`, потому что именно это нужно правилу «не больше трёх
открытых вопросов». Если бы интерфейс проектировала инфраструктура, там появилось бы что-то
вроде `ExecuteScalar(string sql, object parameters)` — технически универсально и совершенно
бесполезно с точки зрения чтения кода.

Полезная привычка при проектировании порта: написать сначала сценарий, как будто нужные
методы уже есть, и только потом перенести их сигнатуры в интерфейс. Тогда контракт получается
по потребности, а не по возможностям инструмента.

## Что внутри `Create` стоит разобрать отдельно

### Где генерируется идентификатор

```csharp
var questionId = Guid.NewGuid();

var question = new Question(questionId, questionDto.Title, questionDto.Text,
                            questionDto.UserId, null, questionDto.TagIds);
```

Не база через `SERIAL`/`IDENTITY` и не конструктор сущности, а именно слой сценария.
Выбор осознанный:

- идентификатор известен **до** обращения к базе — его можно записать в лог, вернуть клиенту,
  положить в сообщение для очереди;
- вставка не требует читать сгенерированное значение обратно;
- операция становится ближе к идемпотентной: повтор с тем же `Guid` не создаст дубликат
  при правильном первичном ключе.

Чем платят: `Guid` как первичный ключ занимает 16 байт против 4 у `int`, и случайный порядок
значений фрагментирует индекс при вставке. Если проект дорастёт до нагрузки, где это заметно,
решение известное — `uuid v7`, упорядоченный по времени, в .NET 9 доступен как
`Guid.CreateVersion7()`.

### Маппинг руками

Ни AutoMapper, ни Mapster — присваивание в конструкторе. Для одного метода это короче
и прозрачнее любой библиотеки, и это правильный выбор по умолчанию.

Автомаппер окупается на десятках однотипных преобразований, а платят за него отладкой:
ошибка в правилах маппинга не видна в коде и всплывает в рантайме. Правило: пока маппинг
пишется за минуту — пиши руками.

### Границы в бизнес-правилах

```csharp
if (openUserQuestionsCount > 3)
{
    throw new InvalidOperationException("A user cannot have more than 3 open questions.");
}
```

Момент, на котором стоит задержаться: формулировка «не больше трёх» означает, что при трёх
уже открытых вопросах создание четвёртого должно быть запрещено. Условие `> 3` при трёх
открытых даёт `false` и пропускает — то есть фактический предел получается четыре.
Нужно `>= 3`.

Это иллюстрация общего свойства: **граничные условия не ловятся ни компилятором, ни
анализаторами, ни беглым чтением кода**. Их ловят только тесты, и именно такие правила —
первые кандидаты на покрытие. Заодно понятно, зачем нужна была вся возня с интерфейсами:
проверить это правило можно с заглушкой репозитория, за миллисекунды, без базы.

Второе наблюдение: само число 3 вписано в код. Пока правило одно — терпимо; дальше такие
величины выносят в конфигурацию или в константу домена, чтобы бизнес-правило было видно
в одном месте, а не растворялось в условиях.

### Структурное логирование

```csharp
_logger.LogInformation("Question created with ID: {QuestionId}", questionId);
```

Разница с интерполяцией строки принципиальная, и её стоит понять один раз.

При такой записи в лог уходит **шаблон** `"Question created with ID: {QuestionId}"`
и **отдельное поле** `QuestionId = ...`. Система сбора логов (Seq, Elastic, Application
Insights) сохранит поле как данные, по которым можно искать и группировать: «покажи все
события по этому вопросу», «сколько вопросов создано за час».

При `$"Question created with ID: {questionId}"` получилась бы просто строка. Каждое событие
уникально, группировать нечего, искать можно только подстрокой.

Правило: **в шаблон подставляются только именованные параметры, интерполяции в логировании
не место**. Имена параметров пишутся в PascalCase — это соглашение экосистемы.

На следующем шаге вокруг вызова появится `if (_logger.IsEnabled(LogLevel.Information))`.
Смысл в том, чтобы не вычислять аргументы, когда уровень логирования выключен. Для одного
`Guid` выигрыш нулевой, но приём правильный, если в лог идёт что-то дорогое — сериализация
объекта, выборка из коллекции.

### Ошибки пока сообщаются исключениями

```csharp
throw new ValidationException(validationResult.Errors);          // тип из FluentValidation
throw new InvalidOperationException("A user cannot have ...");   // тип из BCL
```

Здесь курс намеренно оставляет вопрос открытым: единого места, которое превращало бы
исключение в осмысленный HTTP-ответ, ещё нет. Значит и «пустой заголовок», и «сломалась база»
клиент увидит одинаково — как 500.

Это и есть постановка задачи для видео 2.5. Полезно заметить, что проблема не в самих
исключениях, а в отсутствии **границы трансляции**: слой сценариев говорит на языке
предметной области, веб — на языке кодов HTTP, и кто-то должен переводить. Решается это
обычно одним из трёх способов:

- **middleware-обработчик** — ловит исключение на выходе и превращает в ответ (путь 2.5);
- **result-тип** — метод возвращает «успех или ошибку» вместо броска (путь 2.6);
- **ProblemDetails** — стандарт RFC 9457 для тела ответа с ошибкой, ортогонален первым двум.

## Изменения в домене из того же коммита

У `Question` появился конструктор:

```csharp
public Question(Guid id, string title, string text, Guid userId, Guid? screenshotId, IEnumerable<Guid> tagIds)
```

а `required` с `Title`/`Text`/`UserId` снят — обязательность теперь обеспечивает конструктор.

Это шаг от анемичной модели к нормальной: раньше объект можно было собрать в любом
состоянии через инициализатор, теперь есть единственная точка входа, где в будущем можно
проверять инварианты. Сеттеры пока остались публичными, поэтому защита неполная — тема
проектирования сущностей вынесена в отдельное видео 2.15, где появятся `private set`
и методы, меняющие состояние.

Появился `QuestionStatus` — статус вопроса как перечисление вместо строки или числа.
Выигрыш: компилятор не даст присвоить несуществующее значение, а в коде видно все допустимые
состояния сразу.

## Сверка с эталоном

- **`Program.cs` у автора на этом шаге не вызывает `AddProgramDependencies()`** — у тебя
  вызов есть, это правильно.
- Автор бросает голое `new Exception(...)`, у тебя `InvalidOperationException` — твой вариант
  точнее передаёт смысл.
- `GetOpenUserQuestionsCountAsync` против авторского `GetOpenUserQuestionsAsync` — твоё имя
  честнее говорит, что возвращается число.
- `Open`/`Resolved` вместо авторского `OPEN`/`RESOLVED` — соответствует соглашениям .NET.
- Мелочь: `DependecyInjection` — в имени файла и публичного класса потерялась буква `n`,
  в Web-слое то же имя написано верно. Переименуй через рефакторинг IDE, пока на него
  не появилось много ссылок.
