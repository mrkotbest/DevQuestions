## Теория: что такое доменный слой

Домен — это код, который описывает предметную область так, как о ней говорят люди,
а не так, как удобно технологиям. В нём нет ни HTTP, ни SQL, ни JSON. Если убрать из проекта
всё остальное, домен должен остаться осмысленным.

Базовый словарь, который дальше используется постоянно:

**Сущность (Entity)** — объект с идентичностью. Два вопроса с одинаковым текстом — это
два разных вопроса, потому что у них разные `Id`. Сущность живёт во времени: меняет состояние,
оставаясь собой.

**Объект-значение (Value Object)** — объект без идентичности, определяемый только своим
содержимым. Деньги, адрес, диапазон дат, email. Два одинаковых адреса взаимозаменяемы.
В этом проекте их пока нет, но на видео 2.15 тема всплывёт: например, `Title` с ограничением
длины может стать объектом-значением вместо голой строки.

**Агрегат** — группа сущностей, которая изменяется и сохраняется как единое целое. У агрегата
есть **корень** — единственная точка входа: снаружи обращаются только к нему, а внутренности
доступны через него. `Question` — корень агрегата, `Answer` — его часть.

**Инвариант** — утверждение, которое должно быть истинно всегда. «У пользователя не больше
трёх открытых вопросов», «нельзя добавить ответ в закрытый вопрос». Агрегат существует
ровно для того, чтобы было место, где инвариант можно гарантировать: раз всё меняется через
корень, корень может проверить правило.

## Разбор по шагам

### Формат решения `.slnx`

```xml
<Solution>
  <Folder Name="/src/">
    <Project Path="src/DevQuestions.Domain/DevQuestions.Domain.csproj" />
  </Folder>
</Solution>
```

Новый XML-формат решения (SDK 9+) вместо `.sln` с его GUID-простынёй. Читается глазами
и почти не конфликтует при слиянии веток — старый формат при добавлении проектов в двух
ветках конфликтовал регулярно.

Важное и неочевидное: **`.slnx` — это файл для IDE**. Добавление проекта сюда не создаёт
никакой зависимости между проектами. За реальные связи отвечает `ProjectReference` в `.csproj`.
Это разные механизмы, и их полезно не путать с самого начала.

Папка `/src/` в решении зеркалит физическую `src/`. На одном проекте кажется избыточным,
но через два видео проектов станет семь, и разделение на `src/`, `tests/`, `Solution Items`
начнёт экономить время.

### Проект домена

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

Ноль `PackageReference`, ноль `ProjectReference`. Ни EF Core, ни MediatR, ни атрибутов
валидации.

**Главное правило чистой архитектуры здесь обеспечено не соглашением, а отсутствием строк
в файле проекта.** Нечему протащить в домен знание о базе или вебе — просто нет ссылок.
Это редкий случай, когда архитектурное правило проверяется механически: открыл `.csproj`,
увидел пустой список ссылок, значит правило соблюдено.

`ImplicitUsings` — причина, по которой в файлах сущностей нет ни одного `using`:
`Guid`, `List<T>`, `DateTime` подключаются автоматически.

### Сущности

```csharp
public class Question
{
    public Guid Id { get; set; }
    public required string Title { get; set; }
    public required string Text { get; set; }
    public required Guid UserId { get; set; }
    public Guid? ScreenshotId { get; set; }
    public List<Answer> Answers { get; set; } = [];
    public Answer? Solution { get; set; }
    public List<Guid> Tags { get; set; } = [];
}
```

Три приёма, каждый стоит отдельного разбора.

**`required`** — ключевое слово C# 11. Компилятор не даст создать объект, не присвоив такое
свойство:

```csharp
var question = new Question();                          // ошибка компиляции
var question = new Question { Title = "...", ... };     // так можно
```

Применено последовательно: стоит там, где значение обязано быть при создании, и отсутствует
у `Id`, дат, nullable-полей и инициализированных коллекций. Важно понимать границу приёма:
`required` проверяется **в момент конструирования**, и дальше объект живёт как обычно —
`question.Title = null!` компилятор пропустит.

**`= []`** — коллекционное выражение C# 12. Коллекция никогда не `null`, значит в коде
не будет проверок `if (Answers != null)`. Дёшево и заметно сокращает количество мест,
где возможен `NullReferenceException`.

**`{ get; set; }` у всего** — модель пока **анемичная**: данные без поведения.

### Теория: анемичная и богатая модель

Термин ввёл Мартин Фаулер, и звучит он осуждающе, но на практике вопрос сложнее.

**Анемичная модель** — сущности содержат только свойства, вся логика в сервисах:

```csharp
// в сервисе
if (question.Status == QuestionStatus.Resolved)
{
    throw new InvalidOperationException("Нельзя отвечать на закрытый вопрос");
}
question.Answers.Add(answer);
```

Проблема в том, что правило живёт снаружи объекта. Появится второй сервис, который добавляет
ответы, — проверку придётся продублировать, и однажды её забудут. Сама сущность при этом
позволяет привести себя в некорректное состояние.

**Богатая модель** — правило внутри объекта, и обойти его нельзя:

```csharp
public class Question
{
    private readonly List<Answer> _answers = [];
    public IReadOnlyList<Answer> Answers => _answers;   // снаружи только чтение

    public void AddAnswer(Answer answer)
    {
        if (Status == QuestionStatus.Resolved)
        {
            throw new InvalidOperationException("Нельзя отвечать на закрытый вопрос");
        }

        _answers.Add(answer);
    }
}
```

Разница не в количестве кода, а в том, **где гарантируется инвариант**. Во втором варианте
объект невозможно испортить снаружи: коллекция закрыта на изменение, состояние меняется
только через метод, который знает правило.

Почему в курсе начинают с анемичной: богатая модель требует, чтобы сначала были известны
правила. Их пока не сформулировали — они появятся на 2.3 в сценариях, и только на 2.15,
в видео «Проектирование доменных сущностей», переедут внутрь объектов. Это нормальный порядок:
сначала заставить работать, потом навести порядок.

### Как связи выражены и почему по-разному

| Способ | Где применён |
|---|---|
| Ссылка на объект | `Question.Answers`, `Question.Solution`, `Answer.Question`, `Comment.Parent`, `Comment.Children` |
| Идентификатор | `Question.Tags` (`List<Guid>`), `Answer.Comments` (`List<Guid>`), `ScreenshotId`, все `UserId` |

Это прямое отражение теории агрегатов: **внутри агрегата — ссылки на объекты, наружу —
идентификаторы**.

Почему так важно. Ссылка на объект из другого агрегата означает, что их придётся грузить
и сохранять вместе. Один такой переход — и вот уже загрузка вопроса тянет за собой
пользователя, его вопросы, их теги и половину базы. Идентификатор разрывает эту цепочку:
нужен пользователь — сходи за ним отдельно и осознанно.

Второй аргумент — границы транзакций. Классическое правило DDD: **одна транзакция изменяет
один агрегат**. Если агрегаты связаны только идентификаторами, это правило легко соблюсти.

Отсюда видно и то, что в модели пока не устоялось: `Answer.Comments` — это список `Guid`,
то есть комментарии считаются отдельным агрегатом, а `Comment.Children` — список объектов,
то есть внутри агрегата комментариев. Определиться с этим — хорошее упражнение на 2.15.

## На что обратить внимание при развитии модели

Четыре места, где при дальнейшей работе придётся принять решение. Это не ошибки — это
вопросы, ответы на которые дают следующие видео.

**Двусторонняя связь `Question ↔ Answer`.** `Answer.Question` помечен `required`, то есть
ответ нельзя создать без вопроса, а вопрос содержит список ответов. Отсюда два следствия:
порядок сборки графа становится важен, а прямая сериализация в JSON зациклится, если
не настроить `ReferenceHandler.Preserve`. Обратная ссылка нужна EF Core далеко не всегда —
часто её убирают как лишнюю связность.

**`Comment.EntityId` — ссылка без указания типа.** Комментарий относится к вопросу или
к ответу, но по значению `Guid` понять это нельзя, а ссылочную целостность в базе для такой
связи не построить. Варианты решения: раздельные таблицы `question_comments` /
`answer_comments`; пара `EntityId` + `EntityType`; наследование таблиц. У каждого своя цена,
и выбор зависит от того, нужны ли будут запросы «все комментарии пользователя» независимо
от типа объекта.

**Отсутствие `User`.** Идентификатор пользователя встречается в четырёх сущностях, а самой
сущности нет. Это нормально, когда пользователи живут в отдельном модуле или сервисе —
и как раз к такой схеме курс придёт на 2.10. Главное, чтобы это было решением, а не забывчивостью.

**Временные метки только у `Report`.** У вопросов, ответов и комментариев нет `CreatedAt`,
хотя сортировка по дате — основной сценарий любого Q&A-сайта. Обычно такие поля выносят
в общий базовый класс или интерфейс, а заполняют автоматически — например, перехватом
в `SaveChanges` у EF Core.

**`Id` без значения по умолчанию.** Только что созданная сущность имеет `Id == Guid.Empty` —
кто присваивает идентификатор, пока не решено. На 2.3 выяснится, что это делает слой сценариев,
и там же разбирается, почему не база.

## Сверка с эталоном

Совпадает с автором свойство в свойство, включая `required`, `= []` и nullable-поля.
Расхождений нет.
