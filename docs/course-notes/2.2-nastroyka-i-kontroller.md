## Теория: как MSBuild собирает проект

Чтобы понять смысл `Directory.Build.props`, нужно знать, из чего вообще складывается сборка.

Файл `.csproj` — это скрипт для MSBuild. Строка `<Project Sdk="Microsoft.NET.Sdk">` подключает
**SDK** — набор готовых правил: какие файлы компилировать, куда складывать результат, как
восстанавливать пакеты. Именно поэтому современный `.csproj` такой короткий: всё общее уже
описано в SDK, в проекте остаются только отличия.

`Directory.Build.props` — механизм ещё на уровень выше. MSBuild при сборке **любого** проекта
поднимается вверх по дереву каталогов, находит первый такой файл и подставляет его содержимое
**до** содержимого `.csproj`. Есть и парный `Directory.Build.targets`, он подставляется
**после** — туда кладут то, что должно переопределять настройки проектов.

Практический результат: после переезда файл проекта домена выглядит так:

```xml
<Project Sdk="Microsoft.NET.Sdk">
</Project>
```

и при этом собирается в `net10.0` с включённым `Nullable`.

Зачем это нужно: обновление версии фреймворка становится правкой одной строки вместо семи,
а новый проект автоматически получает те же настройки — забыть включить `Nullable` невозможно.

Обрати внимание на порядок в истории коммитов: в 2.1 свойства были написаны в единственном
`.csproj`, и только здесь вынесены наверх. Автор намеренно показывает **рефакторинг**,
а не готовый результат — в своём проекте ты пройдёшь этот путь точно так же.

### Что ещё обычно кладут в этот файл

```xml
<PropertyGroup>
  <LangVersion>latest</LangVersion>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>   <!-- предупреждение = ошибка сборки -->
  <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

`EnforceCodeStyleInBuild` заслуживает отдельного слова. По умолчанию он выключен, и это
означает, что правила из `.editorconfig` вида `csharp_style_*` и `dotnet_style_*` работают
**только в редакторе** — подсвечивают, но сборку не ломают. Правила анализаторов вроде
StyleCop (`SA####`) работают иначе: это обычные пакеты-анализаторы, они проверяются при сборке
всегда.

То есть настройка стиля фактически двухуровневая: анализаторы обязательны, правила
`.editorconfig` — рекомендация, пока это свойство не включено. Включать его стоит вместе
с `TreatWarningsAsErrors` и только на чистом коде, иначе получишь сотни ошибок разом.

## Теория: анализаторы и .editorconfig

**Анализатор** — это плагин к компилятору Roslyn, который во время сборки разбирает
синтаксическое дерево и выдаёт диагностики. Три главных семейства:

| Префикс | Откуда | О чём |
|---|---|---|
| `CS####` | сам компилятор | ошибки и предупреждения языка |
| `CA####` | встроенные .NET-анализаторы | качество кода: производительность, безопасность, надёжность |
| `IDE####` | правила стиля из `.editorconfig` | форматирование и предпочтения синтаксиса |
| `SA####` | StyleCop.Analyzers (пакет) | оформление: порядок членов, документация, пробелы |

`.editorconfig` — общий для всех редакторов формат, но в .NET он используется ещё и как
конфигурация анализаторов: там задаются и правила стиля, и серьёзность любой диагностики:

```ini
dotnet_diagnostic.CA1822.severity = warning     # поднять конкретное правило
dotnet_analyzer_diagnostic.category-security.severity = error   # целую категорию
```

### Почему в файле 16 подавлений StyleCop

```
SA1000 SA1010 SA1011 SA1024 SA1101 SA1106 SA1200 SA1201
SA1206 SA1309 SA1310 SA1313 SA1503 SA1600 SA1601 SA1633
```

Причина в возрасте пакета: StyleCop.Analyzers 1.1.118 — последняя стабильная версия, вышла
в 2018 году. Она не знает ни записей, ни file-scoped namespace, ни `required`, ни коллекционных
выражений. Поэтому SA1313 ругается на `CreateQuestionDto(string Title, ...)` — для него `Title`
это параметр с большой буквы; SA1010/SA1011 срабатывают на `= []`; SA1206 не знает, куда
поставить `required` в порядке модификаторов.

Ещё три подавления — примирение двух наборов правил, которые требуют противоположного:

| Подавлено | Чего требует StyleCop | Что выбрал автор в `.editorconfig` |
|---|---|---|
| SA1101 | писать `this.Method()` | без `this.` |
| SA1200 | `using` **внутри** namespace | `using` снаружи |
| SA1309, SA1310 | имя поля не начинается с `_` | `_camelCase` для приватных полей |

Вывод, который переносится в свои проекты: **длинный список подавлений обычно означает,
что анализатор не подходит проекту, а не что код плохой**. Современные альтернативы StyleCop —
встроенные IDE-правила с `EnforceCodeStyleInBuild`, либо актуальные наборы
`Roslynator` и `Meziantou.Analyzer`.

## Теория: почему контроллеры вынесены в отдельный проект

```xml
<Project Sdk="Microsoft.NET.Sdk">          <!-- обычная библиотека, НЕ .Web -->
  <ItemGroup>
    <FrameworkReference Include="Microsoft.AspNetCore.App" />
  </ItemGroup>
```

Обычно контроллеры лежат в веб-проекте. Здесь они вынесены в `DevQuestions.Presenters`,
и смысл этого разделения такой:

- **Хост перестаёт владеть формой API.** В `DevQuestions.Web` остаётся только композиция:
  16 строк `Program.cs` и три JSON-файла. Он отвечает за «как запустить», а не за «что отдать».
- **Контроллеры становятся заменяемыми.** Появится второй хост (например, для тестов или
  отдельного набора эндпоинтов) — он подключит тот же проект.
- **Видно границу.** Веб-слой в терминах чистой архитектуры — это внешнее кольцо, и то,
  что он вынесен в отдельную сборку, делает границу физической.

### Что такое FrameworkReference

Обычные библиотеки не могут просто так использовать типы ASP.NET Core: они лежат не в базовом
рантайме .NET, а в **shared framework** — отдельном наборе сборок, который устанавливается
вместе с ASP.NET Core.

`<FrameworkReference Include="Microsoft.AspNetCore.App" />` говорит: «дай этой библиотеке
доступ к сборкам ASP.NET Core, но не копируй их в вывод — они и так будут на машине,
где приложение запускается».

Это канонический способ начиная с .NET Core 3.0. До этого ставили пакет
`Microsoft.AspNetCore.Mvc.Core` — так до сих пор делает автор курса, и это устаревший приём:
тот пакет остановился на версии 2.2.5 и снят с поддержки.

### Как контроллеры из библиотеки вообще находятся

Самый неочевидный механизм этого шага. В `Program.cs` написано просто `AddControllers()`,
никакого указания на сборку. Откуда MVC знает, где искать?

MVC ищет контроллеры не по всем загруженным сборкам, а по списку **Application Parts** —
зарегистрированных «частей приложения». Web SDK при сборке просматривает все `ProjectReference`,
находит те, что ссылаются на MVC, и генерирует в хост-сборку атрибут:

```csharp
// obj/Debug/net10.0/DevQuestions.Web.MvcApplicationPartsAssemblyInfo.cs — создаётся сборкой
[assembly: ApplicationPartAttribute("DevQuestions.Presenters")]
```

Практический вывод: связь «Web → Presenters» держится на `ProjectReference`, и именно поэтому
он там нужен, хотя в коде хоста ни один тип из Presenters не упоминается. Если понадобится
подключить контроллеры из сборки, на которую нет ссылки (например, из плагина), это делается
явно:

```csharp
builder.Services.AddControllers()
    .AddApplicationPart(typeof(SomeController).Assembly);
```

## Contracts: зачем отдельный проект под DTO

```csharp
public record CreateQuestionDto(string Title, string Body, Guid UserId, Guid[] TagIds);
public record UpdateQuestionDto(string Title, string Body, Guid[] TagIds);
public record AddAnswerDto(Guid UserId, string Text);
public record GetQuestionsDto(string Search, Guid[] TagIds, int PageSize, int Limit);
```

**DTO (Data Transfer Object)** — объект, единственная задача которого перенести данные через
границу. У него нет поведения, он не участвует в бизнес-правилах.

Почему их не заменить доменными сущностями:

1. **Домен меняется чаще контракта.** Переименование поля в сущности не должно ломать клиентов.
2. **Домен знает лишнее.** Внутренние флаги, идентификаторы связанных агрегатов, аудит —
   всё это утечёт наружу без единой строчки кода.
3. **Формы разные.** При создании нужен заголовок и не нужен идентификатор; при чтении наоборот.
   Одна модель на оба случая всегда получается компромиссной.

Почему это **отдельный проект**, а не папка: у него ноль зависимостей, поэтому сборку
`DevQuestions.Contracts.dll` можно отдать клиенту как есть — например, чтобы фронтенд
на .NET или другой сервис не описывали типы руками.

### Почему record, а не class

```csharp
public record CreateQuestionDto(string Title, string Body, Guid UserId, Guid[] TagIds);
```

Позиционная запись даёт в одной строке: неизменяемые свойства (`init`-сеттеры), конструктор,
сравнение по значению, `ToString()` с содержимым и деконструкцию. Для DTO это ровно то,
что нужно — их не мутируют после создания.

Мелочь, которую стоит заметить: `Guid[]` на границе и `List<Guid>` в домене. Массив естественен
для JSON и не предполагает изменения, список удобнее внутри. Разные задачи — разные типы.

### Как эти типы попадают в запрос

**Model binding** — механизм ASP.NET Core, который заполняет параметры метода из HTTP-запроса.
Источники указаны явно:

```csharp
public async Task<IActionResult> Create([FromBody] CreateQuestionDto dto, CancellationToken ct)
public async Task<IActionResult> GetAll([FromQuery] GetQuestionsDto dto, CancellationToken ct)
public async Task<IActionResult> GetById([FromRoute] Guid id, CancellationToken ct)
```

`[ApiController]` вывел бы их и сам (сложные типы — из тела, простые — из маршрута), но
в учебном коде явная запись полезнее: видно намерение.

Важное свойство, про которое стоит знать заранее: **model binding не смотрит на nullable-аннотации**.
`Search` объявлен как non-nullable `string`, но если параметра нет в query-строке, туда придёт
`null` — компилятор об этом не предупредит, потому что заполняет поле не код, а рефлексия.
Отсюда привычка давать таким полям значение по умолчанию или помечать их `?`.

## Контроллер

```csharp
[ApiController]
[Route("[controller]")]
public class QuestionsController : ControllerBase
```

| Маршрут | Метод |
|---|---|
| `POST /Questions` | `Create` |
| `GET /Questions` | `GetAll` |
| `GET /Questions/{id:guid}` | `GetById` |
| `PUT /Questions/{id:guid}` | `Update` |
| `DELETE /Questions/{id:guid}` | `Delete` |
| `PUT /Questions/{id:guid}/solution` | `SelectSolution` |
| `POST /Questions/{id:guid}/answers` | `AddAnswer` |

Решения, которые стоит разобрать:

**`ControllerBase`, а не `Controller`.** Второй добавляет всё, что нужно для представлений:
`View()`, `ViewBag`, работу с razor. Для API это мёртвый груз — `ControllerBase` даёт только
`Ok()`, `NotFound()`, `CreatedAtAction()` и доступ к `HttpContext`.

**Ограничение `:guid` в маршруте.** Запрос `/Questions/abc` не дойдёт до метода: маршрутизация
не найдёт подходящий шаблон и вернёт 404. Без ограничения запрос попал бы в метод и упал
на разборе параметра.

**`[ApiController]`** включает набор поведений: автоматический 400 при ошибке привязки модели,
вывод источников параметров, ответы в формате ProblemDetails. Этот же атрибут позже избавит
от ручных проверок `ModelState`.

**`CancellationToken` в каждом методе с самого начала.** Пока асинхронной работы нет, но
привычка правильная: когда клиент разрывает соединение, ASP.NET Core отменяет токен, и запрос
к базе не продолжает занимать ресурсы. Добавлять этот параметр в сорок методов потом —
занятие неблагодарное.

**Вложенные маршруты по принадлежности.** `POST /Questions/{id}/answers` — ответ не существует
без вопроса, поэтому живёт внутри него. Глубже двух уровней обычно не уходят.

### Что стоит сделать иначе в реальном API

- **Префикс и версия.** `[Route("api/v1/[controller]")]` вместо `[Route("[controller]")]`.
  Добавить версионирование потом — ломающее изменение для всех клиентов, поэтому его
  закладывают сразу, даже если версия долго остаётся первой.
- **Коды ответов по смыслу.** `Create` должен возвращать `CreatedAtAction(...)` — это 201
  плюс заголовок `Location` со ссылкой на созданный ресурс. `Delete` — `NoContent()` (204).
  Сейчас везде `Ok()`, потому что тема кодов ответа разбирается на видео 2.5.
- **`[ProducesResponseType]`** — атрибуты, описывающие возможные ответы. Они попадают
  в OpenAPI-схему, и клиентские генераторы кода начинают понимать, что метод может вернуть 404.

## Хост

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddOpenApi();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
    app.UseSwaggerUI(options => options.SwaggerEndpoint("/openapi/v1.json", "DevQuestions API"));
}

app.MapControllers();
app.Run();
```

Здесь два этапа, и разделяет их `builder.Build()`:

1. **До** — настройка контейнера: что вообще умеет приложение (`builder.Services`).
2. **После** — настройка конвейера обработки запроса: через что проходит каждый HTTP-запрос
   (`app.Use...`, `app.Map...`).

Порядок во второй части важен — middleware выполняются в том порядке, в котором записаны.

### Про OpenAPI

`AddOpenApi()` — встроенный в .NET 9/10 генератор документа (пакет `Microsoft.AspNetCore.OpenApi`),
а от Swashbuckle подключён **только UI** (`Swashbuckle.AspNetCore.SwaggerUI`, не весь пакет).

Это актуальная рекомендация Microsoft: схему генерирует платформа, стороннюю библиотеку
оставляют для отрисовки страницы. Поэтому в `SwaggerEndpoint` указан путь `/openapi/v1.json`,
а не привычный по старым проектам `/swagger/v1/swagger.json`.

Обе конечные точки под `IsDevelopment()` — в продакшене схема API наружу не отдаётся.

### Чего в конвейере пока нет

`UseHttpsRedirection`, аутентификация, CORS, обработчик исключений, настройка логирования.
Полезно увидеть, что для работающего API ничего из этого формально не обязательно —
и что каждый следующий элемент добавляется, когда появляется конкретная задача, а не «потому
что так принято».

## Мелочь в домене из того же коммита

```diff
 public enum Status
 {
-    Open,
+    Open = 0,
-    InProgress,
+    InProgress = 1,
```

Значения те же, что подставились бы автоматически. Смысл в том, чтобы **зафиксировать числа**:
в базе хранится именно число, и перестановка членов перечисления молча изменила бы смысл уже
сохранённых данных. Явные значения превращают такое изменение в осознанное.

Логичное продолжение — `enum Status : byte`. Хранилище перечисления по умолчанию `int`
(4 байта), для статуса с четырьмя значениями хватает одного.

## Сверка с эталоном

- Автор использует устаревший `Microsoft.AspNetCore.Mvc.Core 2.2.5`, у тебя `FrameworkReference` —
  твой вариант соответствует современной практике.
- `GetQuestionsDto`: у автора `(Search, TagIds, Page, PageSize)`, у тебя `(… PageSize, Limit)`.
  `PageSize` и `Limit` означают одно и то же, номера страницы в этой паре нет — стоит привести
  к авторскому варианту до видео 2.9, где начнётся пагинация.
- Пространство имён у автора `DevQuestion.Contracts` (без `s`) — опечатка, которая доживёт
  до последних веток курса. Твоё написание правильное.
