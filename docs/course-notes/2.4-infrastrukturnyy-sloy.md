## Теория: порты и адаптеры

Терминология пришла из гексагональной архитектуры Алистера Кокбёрна и описывает тот же
механизм, что и «инверсия зависимостей» у Мартина.

**Порт** — интерфейс, который объявляет **потребитель**. Он сформулирован на языке задачи:
«мне нужно сохранить вопрос», «мне нужно проиндексировать текст». Про технологию порт
не знает ничего.

**Адаптер** — реализация порта под конкретную технологию. Он переводит язык задачи на язык
инструмента: `AddAsync(question)` превращается в `INSERT INTO questions ...`.

```csharp
// Порт — Application говорит, что ему нужно
public interface ISearchProvider
{
    Task<List<Guid>> SearchAsync(string query);
    Task IndexQuestionAsync(Question question);
}

// Адаптер — Infrastructure говорит, чем это будет сделано
public class ElasticSearchProvider : ISearchProvider { ... }
```

Посмотри на направление ссылок в файлах проектов: `Infrastructure.ElasticSearch` ссылается
на `Application`, а не наоборот. Application про Elasticsearch не знает ни типа, ни пакета,
ни строки подключения.

Метафора «гексагон» означает вот что: приложение — это ядро, по периметру которого расставлены
порты. Каждый порт можно закрыть разными адаптерами, и ядро не заметит подмены. Тесты
подставляют заглушки в те же порты, что и продакшен — реальные адаптеры.

Подробный разбор самого принципа — в [теории про инверсию зависимостей](teoriya-dependency-injection.md).

## Почему автор объявил сразу три порта

Здесь есть педагогический замысел: один пример инверсии выглядит как случайность,
три — как система.

| Порт | Адаптер | Что за внешний мир |
|---|---|---|
| `IQuestionsRepository` | `QuestionsEfCoreRepository`, `QuestionsSqlRepository` | реляционная БД |
| `ISqlConnectionFactory` | `SqlConnectionFactory` | соединение с Postgres |
| `ISearchProvider` | `ElasticSearchProvider` | поисковый движок |
| `IFileProvider` | `S3Provider` | объектное хранилище |

Все четыре — принципиально разные технологии, но приём один и тот же. Именно повторение
показывает, что это не частное решение для базы данных, а способ обращения с любой внешней
зависимостью: очередью сообщений, платёжным шлюзом, отправкой почты.

И обрати внимание на побочный эффект: **четыре интерфейса в Application — это полный список
того, что приложение требует от внешнего мира**. Не надо читать весь код, чтобы понять,
с чем система интегрируется. Это одна из самых недооценённых выгод подхода.

### Почему порты названы так, а не иначе

```csharp
public interface ISqlConnectionFactory
{
    IDbConnection Create();
}
```

Метод возвращает `System.Data.IDbConnection` — тип из базовой библиотеки .NET. Благодаря
этому Application не нуждается ни в каком новом пакете: контракт выражен в терминах,
которые есть у всех.

Если бы порт возвращал `NpgsqlConnection`, зависимость от Npgsql протекла бы в слой сценариев,
и вся конструкция потеряла бы смысл — формально интерфейс есть, фактически Application
привязан к Postgres. Это тонкий момент, который стоит держать в голове: **тип возвращаемого
значения — такая же часть зависимости, как ссылка на проект**.

## Теория: два репозитория на один порт

Один интерфейс `IQuestionsRepository` — две реализации: на EF Core и на Dapper. Это не
избыточность, а демонстрация классического разделения.

### Чем они отличаются по сути

**EF Core — полноценная ORM с отслеживанием изменений.**

```csharp
var question = await _dbContext.Questions
    .Include(q => q.Answers)
    .FirstOrDefaultAsync(q => q.Id == questionId, cancellationToken);

question.Title = "новый заголовок";
await _dbContext.SaveChangesAsync(cancellationToken);   // UPDATE сгенерируется сам
```

Контекст запоминает, в каком состоянии сущность была загружена, сравнивает с текущим и сам
строит `UPDATE` только по изменённым колонкам. Это называется **change tracking**, и за него
платят памятью и временем на сравнение.

`DbContext` заодно является реализацией паттерна **Unit of Work**: все изменения, сделанные
за время запроса, накапливаются и уходят в базу одной транзакцией при `SaveChanges()`.

**Dapper — микро-ORM, он же «умный маппер».**

```csharp
const string sql =
    """
    INSERT INTO questions (id, title, text, user_id, screenshot_id, tags, status)
    VALUES (@Id, @Title, @Text, @UserId, @ScreenshotId, @Tags, @Status)
    """;

using var connection = _sqlConnectionFactory.Create();
await connection.ExecuteAsync(sql, new { question.Id, question.Title, ... });
```

Никакого отслеживания, никакой генерации SQL — ты пишешь запрос сам, Dapper лишь раскладывает
параметры и собирает результат в объекты. Быстрее и предсказуемее, но всю работу по
сопоставлению делаешь руками.

### Откуда берётся правило «EF на запись, Dapper на чтение»

- **Запись** — это загрузить агрегат, изменить, сохранить в транзакции. Здесь отслеживание
  изменений экономит много ручного кода, а объёмы данных маленькие: один вопрос, один ответ.
- **Чтение** — это «отдай список с фильтрами, сортировкой и пагинацией». Отслеживание здесь
  не нужно вообще (сущности никто не собирается менять), а SQL, который EF генерирует для
  сложных выборок с джойнами, бывает неуправляемо тяжёлым. Прямой запрос быстрее и, главное,
  предсказуем — ты видишь ровно то, что уйдёт в базу.

Отсюда и появилось разделение, к которому курс придёт на видео 2.9: там возникнет отдельный
`IQuestionsReadDbContext`, то есть разделение переедет на уровень интерфейсов.

Промежуточный шаг для EF, который стоит знать уже сейчас:

```csharp
await _dbContext.Questions.AsNoTracking().ToListAsync(cancellationToken);
```

`AsNoTracking()` отключает отслеживание для конкретного запроса и часто закрывает вопрос
производительности чтения без привлечения второй библиотеки.

### Как держать две реализации одновременно

Сейчас зарегистрирована одна — в стандартном контейнере .NET при двух регистрациях одного
интерфейса побеждает последняя. Когда понадобятся обе, есть два пути:

```csharp
// 1. Именованные регистрации (.NET 8+)
services.AddKeyedScoped<IQuestionsRepository, QuestionsEfCoreRepository>("ef");
services.AddKeyedScoped<IQuestionsRepository, QuestionsSqlRepository>("sql");
// потребитель: [FromKeyedServices("sql")] IQuestionsRepository repository

// 2. Разные интерфейсы под разные задачи
services.AddScoped<IQuestionsWriteRepository, QuestionsEfCoreRepository>();
services.AddScoped<IQuestionsReadRepository, QuestionsSqlRepository>();
```

Второй вариант обычно лучше: намерение видно прямо в типе, и случайно записать через
read-репозиторий невозможно. Общее правило — **если у двух реализаций одного интерфейса
разное назначение, интерфейсов должно быть два**.

## Теория: зачем нужен DbContext и что с ним делают дальше

```csharp
public class QuestionsDbContext : DbContext
{
    public DbSet<Question> Questions { get; set; }
}
```

`DbContext` выполняет три роли сразу: описывает модель данных, отслеживает изменения
и играет роль единицы работы (транзакции). `DbSet<Question>` — точка входа для запросов
к таблице вопросов.

Дальше по мере развития проекта к этому классу добавляют три вещи.

**1. Конфигурация подключения.** Регистрация с указанием провайдера:

```csharp
services.AddDbContext<QuestionsDbContext>(options =>
    options.UseNpgsql(configuration.GetConnectionString("Database")));
```

плюс конструктор `QuestionsDbContext(DbContextOptions<QuestionsDbContext> options) : base(options)`.
Строка подключения при этом живёт в `appsettings.json`, а секреты — в user secrets
или переменных окружения, но не в репозитории.

**2. Конфигурации сущностей.** Самое интересное и содержательное.

Домен спроектирован под бизнес-смысл, а не под базу данных: у `Question` есть конструктор
с параметрами, коллекция `Tags` из `Guid`, две связи с `Answer` (список ответов и выбранное
решение). EF по соглашениям такую модель однозначно разобрать не сможет — и это **не проблема
домена, а нормальная ситуация**. Мост между ними называется конфигурацией:

```csharp
public class QuestionConfiguration : IEntityTypeConfiguration<Question>
{
    public void Configure(EntityTypeBuilder<Question> builder)
    {
        builder.ToTable("questions");
        builder.HasKey(q => q.Id);

        builder.Property(q => q.Title).HasMaxLength(500).IsRequired();

        // какая из двух связей с Answer — список ответов
        builder.HasMany(q => q.Answers)
               .WithOne(a => a.Question)
               .HasForeignKey("question_id");

        // а какая — выбранное решение
        builder.HasOne(q => q.Solution).WithMany().HasForeignKey("solution_id");

        // список идентификаторов тегов — в массив uuid[] Postgres
        builder.Property(q => q.Tags).HasColumnType("uuid[]");
    }
}
```

и подключение всех сразу:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.ApplyConfigurationsFromAssembly(typeof(QuestionsDbContext).Assembly);
}
```

Именно поэтому в проекте заранее заведена папка `Configurations` — под этот шаг.

Ключевая мысль: **настройка хранения вынесена из домена**. Сущность не знает про таблицы,
колонки и типы Postgres — ни одного атрибута вроде `[Table]` или `[Column]` в ней нет.
Альтернативный подход (Data Annotations прямо в сущности) короче, но он протаскивает знание
о базе в доменный слой, а вместе с ним и ссылку на пакет EF Core.

**3. Миграции.** Когда конфигурации готовы, схема базы создаётся из модели:

```bash
dotnet ef migrations add InitialCreate --project src/DevQuestions.Infrastructure.PostgreSql --startup-project src/DevQuestions.Web
dotnet ef database update --project src/DevQuestions.Infrastructure.PostgreSql --startup-project src/DevQuestions.Web
```

Два проекта указываются потому, что модель живёт в инфраструктуре, а строка подключения
и корень композиции — в веб-проекте.

### Когда DbContext действительно обращается к базе

Полезное свойство, которое объясняет поведение приложения при первых запусках: **создание
`DbContext` ничего не делает**. Ни соединения, ни проверки настроек — объект создаётся
мгновенно и лениво.

Модель строится и проверяется при **первом обращении к `DbSet`**, а соединение открывается
ещё позже — когда запрос выполняется (`ToListAsync`, `FirstOrDefaultAsync`, `SaveChangesAsync`).
Поэтому:

```csharp
var context = new QuestionsDbContext();                    // ок, ничего не произошло
var query = context.Questions.Where(q => q.Id == id);      // ок, LINQ только строит дерево выражения
var question = await query.FirstOrDefaultAsync();          // вот здесь идёт работа с базой
```

Отсюда практическое следствие: сообщение вроде `No database provider has been configured
for this DbContext` появляется не при старте приложения и не при создании контекста,
а ровно в той строке, где впервые понадобилась модель. В стеке вызовов это будет выглядеть
как падение внутри `Include(...)` или `FirstOrDefaultAsync(...)` — хотя причина находится
в регистрации контейнера.

Тот же принцип объясняет и другое частое наблюдение: путь выполнения до базы вообще может
не дойти. Если сценарий начинается с валидации, то при некорректных входных данных он
завершится на ней, и ни одна строка с EF не выполнится. Одно и то же приложение на валидном
и невалидном запросе покажет совершенно разное поведение — и это не признак поломки,
а порядок шагов в сценарии.

Отладочный приём на будущее: включить логирование SQL, чтобы видеть, что именно EF отправляет
в базу и когда:

```csharp
services.AddDbContext<QuestionsDbContext>(options =>
    options.UseNpgsql(connectionString)
           .LogTo(Console.WriteLine, LogLevel.Information)
           .EnableSensitiveDataLogging());   // показывает значения параметров, только для разработки
```

## Сидеры: зачем они и как устроены

```csharp
public interface ISeeder
{
    Task SeedAsync();
}
```

```csharp
public static async Task<WebApplication> Seed(this WebApplication app)
{
    using var scope = app.Services.CreateScope();

    var seeders = scope.ServiceProvider.GetServices<ISeeder>();

    foreach (var seeder in seeders)
    {
        await seeder.SeedAsync();
    }

    return app;
}
```

Сидер — это наполнение базы начальными данными: справочники, тестовые записи, учётная запись
администратора. Конструкция выбрана удачно и стоит разбора.

**Почему интерфейс, а не один метод.** Каждый сидер отвечает за свою область (вопросы, теги,
пользователи), а цикл работает с любым их количеством. Добавление нового сидера — это новый
класс и одна регистрация, без правки цикла.

**Зачем `CreateScope()`.** `WebApplication.Services` — это корневой контейнер, он живёт всё
время работы приложения. Scoped-сервисы (а `DbContext` именно такой) из него напрямую брать
нельзя: они никогда не будут освобождены. Создание области решает это — по выходу из `using`
все Scoped-объекты корректно закрываются, соединение возвращается в пул.

Этот приём нужен везде, где Scoped-сервис требуется вне HTTP-запроса: фоновые задачи,
`IHostedService`, обработчики очередей.

**Возврат `app` для цепочки.** Позволяет писать `await app.Seed();` в общем потоке настройки,
как принято в остальных расширениях ASP.NET Core.

Подключается это в `Program.cs` между сборкой приложения и запуском:

```csharp
var app = builder.Build();

await app.Seed();

app.MapControllers();
app.Run();
```

Плюс регистрация самих сидеров — чтобы цикл нашёл их в контейнере:

```csharp
services.AddScoped<ISeeder, QuestionsSeeder>();
```

Полезно знать про `GetServices<T>()` (множественное число): он возвращает все регистрации
интерфейса и пустую коллекцию, если их нет. В отличие от `GetRequiredService<T>()`, который
в такой ситуации бросает исключение. Для сидеров пустой список — нормальный сценарий, поэтому
выбран именно первый вариант.

## Как контейнер узнаёт про адаптеры

У каждого инфраструктурного проекта — свой метод регистрации, по тому же образцу, что
у Application:

```csharp
// src/DevQuestions.Infrastructure.PostgreSql/DependencyInjection.cs
public static IServiceCollection AddPostgreSqlInfrastructure(this IServiceCollection services)
{
    services.AddScoped<IQuestionsRepository, QuestionsEfCoreRepository>();
    services.AddDbContext<QuestionsDbContext>();

    return services;
}
```

Для остальных проектов это будет выглядеть так же:

```csharp
// src/DevQuestions.Infrastructure.ElasticSearch/DependencyInjection.cs
public static IServiceCollection AddElasticSearchInfrastructure(this IServiceCollection services)
{
    services.AddScoped<ISearchProvider, ElasticSearchProvider>();

    return services;
}
```

Плюс два обязательных условия, без которых регистрация не сработает: `ProjectReference`
из `DevQuestions.Web.csproj` на проект адаптера и вызов метода в `AddProgramDependencies()`.

Здесь стоит запомнить важное различие: **добавление проекта в `DevQuestions.slnx` и
`ProjectReference` в `.csproj` — это разные вещи**. Первое говорит IDE, что показать
в обозревателе решения; второе создаёт реальную зависимость при сборке. Проект, добавленный
только в `.slnx`, соберётся, но в приложение не попадёт.

Если адаптер не зарегистрирован, а сервис его требует, контейнер сообщит об этом при старте:

```
Unable to resolve service for type 'ISearchProvider' while attempting to activate 'QuestionsService'
```

Это работа `ValidateOnBuild` — механизм подробно разобран в
[теории про DI](teoriya-dependency-injection.md#5-di-контейнер-в-net).

## Как развивать дальше

Порядок, в котором логично наращивать этот слой:

1. **Строка подключения и провайдер** — `UseNpgsql` плюс секция `ConnectionStrings`.
   После этого база становится достижимой.
2. **Конфигурации сущностей** — по классу на агрегат в папке `Configurations`.
3. **Миграции** — схема базы генерируется из модели.
4. **Регистрация сидеров и вызов `app.Seed()`** — появляются данные для ручной проверки.
5. **Реальные реализации `ISearchProvider` и `IFileProvider`** — когда дойдёт дело
   до поиска и загрузки скриншотов.

Пара технических деталей на будущее: для Elasticsearch актуальный клиент —
`Elastic.Clients.Elasticsearch` (пакет `Elasticsearch.Net` относится к предыдущему поколению);
а в Dapper отмену запроса передают через `CommandDefinition`, потому что короткая перегрузка
`ExecuteAsync(sql, param)` токен не принимает:

```csharp
var command = new CommandDefinition(sql, parameters, cancellationToken: cancellationToken);
await connection.ExecuteAsync(command);
```

## Что можно было бы сделать иначе

**Порт мог бы не принимать доменную сущность.** Сейчас `ISearchProvider.IndexQuestionAsync`
принимает `Question`, то есть формат поискового индекса привязан к форме домена. Часто такие
порты принимают отдельную модель (`QuestionSearchDocument`), чтобы изменение сущности
не трогало индексацию.

**Репозиторий — не единственный вариант.** Само наличие `IQuestionsRepository` поверх EF Core
иногда критикуют: `DbSet<T>` уже является репозиторием, а `DbContext` — единицей работы,
так что получается обёртка над обёрткой. Аргумент против репозитория: он ограничивает
возможности LINQ и заставляет плодить методы под каждый сценарий выборки. Аргумент за (и он
здесь весомее): без него Application получает прямую зависимость от EF Core, и вся инверсия
теряет смысл. В курсе выбран второй вариант, и для учебной архитектуры это правильный выбор.

**Сохранение могло бы быть отдельным.** Сейчас `AddAsync` внутри себя вызывает
`SaveChangesAsync` — то есть каждый метод репозитория сам завершает транзакцию. Альтернатива —
вынести это в явный `IUnitOfWork.SaveChangesAsync()`, чтобы один сценарий мог изменить
несколько агрегатов и сохранить их одной транзакцией. Курс придёт к этому на видео 2.8
в виде `ITransactionManager`.

## Сверка с эталоном

Инфраструктура почти файл в файл совпадает с авторской. Твои отличия: Dapper-репозиторий
написан по-настоящему (у автора он закомментирован), проекты лежат внутри `src/`, опечатки
в именах исправлены.

Учти при сравнении: ветка `features/issue-6` у автора содержит **один коммит на два видео** —
инфраструктуру и обработку ошибок. Поэтому его состояние выглядит богаче: там уже лежит
то, что разбирается на 2.5. Подробности в [сверке с эталоном](sverka-s-etalonom.md).
