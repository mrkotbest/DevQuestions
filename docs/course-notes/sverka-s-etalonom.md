## Где твои решения оказались лучше

Эти отличия стоит сохранить — они соответствуют современным практикам .NET.

### Ссылка на ASP.NET Core из библиотеки

```xml
<!-- автор -->
<PackageReference Include="Microsoft.AspNetCore.Mvc.Core" Version="2.2.5" />

<!-- ты -->
<FrameworkReference Include="Microsoft.AspNetCore.App" />
```

Пакет `Mvc.Core 2.2.5` — из эпохи ASP.NET Core 2.2, он давно снят с поддержки. Начиная
с .NET Core 3.0 ASP.NET Core поставляется как **shared framework**, и правильный способ
получить его типы в библиотеке — `FrameworkReference`. Он не копирует сборки в вывод,
потому что они уже есть в рантайме на целевой машине.

### Именование в перечислении

У автора `OPEN`, `RESOLVED`. В .NET принято `PascalCase` для членов перечислений —
`SCREAMING_CASE` пришёл из других экосистем (C, Java-константы). Твой вариант
`Open = 0, Resolved = 1` соответствует и соглашениям Microsoft, и настроенному в проекте StyleCop.

### Имя метода отражает возвращаемое значение

Авторский `GetOpenUserQuestionsAsync` возвращает `Task<int>` — по имени ожидается коллекция
вопросов. Твой `GetOpenUserQuestionsCountAsync` честнее: слово `Count` говорит, что придёт число.

Это часть более общего правила: **имя метода — часть контракта**. Читающий код не должен
открывать определение, чтобы понять, что вернётся.

### Исправленные опечатки

У автора пространство имён `DevQuestions.Application.FulltextSeatch` и метод
`IndexQuesionAsync`. У тебя — `FullTextSearch` и `IndexQuestionAsync`.

Учти на будущее: авторские опечатки живут в его репозитории до последних веток курса.
Когда будешь копировать код из следующих видео, эти имена придётся подправлять под свои.

### Реализованный Dapper-репозиторий

У автора `QuestionsSqlRepository` целиком закомментирован — он показал идею, но не писал код.
У тебя написан рабочий `AddAsync` с параметризованным SQL. Разбор того, зачем вообще две
реализации одного порта — в [разборе 2.4](2.4-infrastrukturnyy-sloy.md).

### Расположение проектов

У автора `Infrastructure.ElasticSearch` и `Infrastructure.S3` лежат **вне** `src/`, рядом
с файлом решения. У тебя — внутри `src/`, как и все остальные. Единая структура читается лучше.

## Что стоит привести к варианту курса

### Параметры пагинации

```csharp
// сейчас
public record GetQuestionsDto(string Search, Guid[] TagIds, int PageSize, int Limit);

// у автора и в общепринятой практике
public record GetQuestionsDto(string Search, Guid[] TagIds, int Page, int PageSize);
```

`PageSize` и `Limit` отвечают на один и тот же вопрос — «сколько записей вернуть». Второго
параметра, отвечающего «откуда начать», в этой паре нет, поэтому запросить вторую страницу
нечем.

Устоявшихся способов нумерации два:

| Пара | Как считается | Где применяется |
|---|---|---|
| `Page` + `PageSize` | `OFFSET (Page - 1) * PageSize LIMIT PageSize` | пользовательские интерфейсы со страницами |
| `Limit` + `Offset` | `OFFSET Offset LIMIT Limit` | API общего назначения |

Есть и третий, курсорный (`cursor` + `limit`), где вместо номера страницы передаётся метка
последней увиденной записи. Он не «съезжает» при вставке новых записей и не деградирует
на больших смещениях, поэтому в лентах используют именно его.

Привести к паре `Page` + `PageSize` стоит до видео 2.9 — там начинается выборка данных,
и весь код фильтрации будет строиться вокруг этих параметров.

### Опечатка в имени класса

`src/DevQuestions.Application/DependecyInjection.cs` — в имени файла и публичного класса
потерялась буква `n`. В Web-слое то же имя написано верно, и сейчас в проекте сосуществуют
два написания. Переименование через рефакторинг IDE занимает секунду; чем позже, тем больше
мест придётся трогать.

## Вторая половина ветки: обработка ошибок

Это не расхождение, а разная точка внутри одной ветки. В `features/issue-6` у автора
**один коммит** — «добавил инфраструктурные слои и обработку ошибок», то есть ветка покрывает
сразу два видео: 2.4 и 2.5. Ты прошёл первое из них, поэтому его ветка выглядит богаче твоей.

Ниже — что именно составляет вторую половину, чтобы было понятно, куда идёт видео 2.5.

### Какую задачу он решает

Сейчас сценарий сообщает о проблемах исключениями:

```csharp
throw new ValidationException(validationResult.Errors);          // тип из FluentValidation
throw new InvalidOperationException("A user cannot have ...");   // тип из BCL
```

а веб-слой не умеет их различать, поэтому обе ситуации превращаются в 500. С точки зрения
клиента «ты прислал пустой заголовок» и «у нас упала база» выглядят одинаково, хотя первое —
его ошибка, а второе — наша.

Проблема не в исключениях как таковых, а в отсутствии **границы трансляции**: Application
говорит на языке предметной области, HTTP — на языке кодов состояния, и кто-то должен
переводить одно в другое.

### Как это устроено у автора

```
src/Shared/Error.cs                                     — типизированная ошибка + ErrorType
Application/Exceptions/{BadRequestException,
                        NotFoundException}.cs            — базовые исключения, несущие Error[]
Application/Questions/Fails/Errors.cs                   — каталог ошибок домена
Application/Questions/Fails/Exceptions/*.cs             — конкретные исключения фичи
Application/Extensions/ValidationExtensions.cs          — FluentValidation → Error[]
Web/Middlewares/ExceptionMiddleware.cs                  — превращение исключения в HTTP-ответ
```

Центральная идея — **ошибка как данные, а не как текст**:

```csharp
public record Error
{
    public string Code { get; }            // машиночитаемый код: "question.too.many"
    public string Message { get; }         // человекочитаемое сообщение
    public ErrorType Type { get; }         // VALIDATION | NOT_FOUND | CONFLICT | FAILURE
    public string? InvalidField { get; }   // какое поле виновато

    public static Error Validation(string? code, string message, string? invalidField = null) => ...
    public static Error NotFound(string? code, string message, Guid? id) => ...
    public static Error Conflict(string? code, string message) => ...
    public static Error Failure(string? code, string message) => ...
}
```

Что это даёт:

- **Код вместо текста.** Клиент реагирует на `question.too.many`, а не разбирает строку —
  сообщение можно переписать или перевести, не ломая интеграцию.
- **Тип определяет статус ответа.** `VALIDATION → 400`, `NOT_FOUND → 404`, `CONFLICT → 409`,
  `FAILURE → 500`. Решение принимается в одном месте, а не в каждом контроллере.
- **Каталог ошибок.** `Errors.Questions.ToManyQuestions()` — все ошибки фичи собраны
  в одном классе, их видно списком.

Сценарий после этого читается так:

```csharp
throw new QuestionValidationException(validationResult.ToErrors());
throw new ToManyQuestionsException();
```

а контроллеры не содержат ни одного `try/catch` — исключение ловит middleware на выходе
из конвейера.

### Пара замечаний, если будешь повторять за видео

В коде автора `BadRequestException` отображается на 500 вместо 400, а вызов
`app.UseExceptionMiddleware()` в `Program.cs` записан дважды подряд. Первое стоит исправить,
второе — просто лишняя регистрация.

### Почему это не выбрасывается на следующем шаге

Важно для мотивации: на видео 2.6 исключения заменяются на `Result`, но `Error`, `ErrorType`,
каталог `Errors` и `ToErrors()` переезжают туда целиком. Меняется только способ доставки
ошибки наверх — по исключению или по возвращаемому значению. Так что работа не пропадёт.

## Где вы совпадаете, и это нормально

Обе реализации на конце 2.4 одинаково не доведены до рабочего состояния: провайдер БД
не сконфигурирован, строки подключения нет, сидеры не подключены. Это не отставание,
а текущая точка курса — инфраструктура собирается по частям, и следующие видео эти части
соединят. Порядок подключения описан в [разборе 2.4](2.4-infrastrukturnyy-sloy.md#как-развивать-дальше).

## Куда идёт курс дальше

Разведано по веткам автора — полезно понимать, зачем делается то, что делается сейчас.

**2.6 Result паттерн** (`features/issue-9`). Подключается `CSharpFunctionalExtensions`,
появляется `Failure` — обёртка над набором ошибок. Сигнатура меняется с `Task<Guid> Create(...)`
на `Task<Result<Guid, Failure>> Create(...)`, и каждый `throw` превращается в `return`.
Смысл перехода: ожидаемая ошибка перестаёт быть исключительной ситуацией и становится
частью контракта метода — компилятор заставляет её обработать. `ExceptionMiddleware` при этом
остаётся страховкой от по-настоящему непредвиденных исключений, и две стратегии сосуществуют
осознанно.

**2.8 Разделение на Handlers** (`features/issue-11`). `QuestionsService` разбирается
на вертикальные срезы: папка на фичу, внутри — команда-record, обработчик и валидатор.
Появляются `ICommandHandler<TResponse, TCommand>` и `IQueryHandler<...>`, а ручная регистрация
заменяется сканированием сборки через Scrutor. Тогда же приходит разделение чтения и записи:
`IQuestionsReadDbContext` рядом с обычным контекстом и `ITransactionManager`.

Практический вывод на сейчас: **`IQuestionsService` — временная конструкция**. Не стоит
вкладываться в его развитие, к 2.8 он будет разобран на обработчики.

**2.10 Модульный монолит** (`decorators` → `main`). Валидация уезжает из обработчиков
в декоратор: `services.Decorate(typeof(ICommandHandler<,>), typeof(ValidationDecorator<,>))`.
Декораторы стакаются и включаются маркерными интерфейсами — команда сама объявляет, чем её
оборачивать. Дерево проектов перестраивается в вертикальные модули `src/Questions/`,
`src/Tags/`, `src/Comments/` плюс общий `src/Core/`, и модули общаются через контракты,
а не через прямые ссылки на проекты.
